# Process model

Mithu's Servo edition follows the Chromium process model where Servo already implements the corresponding mechanism. The notes below were checked against a sparse checkout of Chromium (`docs/process_model_and_site_isolation.md`, `docs/mojo_and_services.md`, `base/threading/thread.h`, `base/task/thread_pool.h`, `content/browser/browser_main_loop.h`, `content/public/browser/render_process_host.h`, `services/network/README.md`, `services/network/resource_scheduler/README.md`, `net/http/http_cache.h`, `third_party/blink/renderer/platform/scheduler/README.md`, `page_scheduler.h`, and `page_discarding_helper.h`).

| Chromium | What it does | Mithu |
| --- | --- | --- |
| Browser process vs renderer process | The browser process owns the UI and is privileged. Each site instance (scheme + eTLD+1 in a browsing context group) gets its own renderer on desktop. Renderers talk to the browser over Mojo IPC. Chrome also keeps a spare renderer and a process limit, and reuses a process when the limit is hit. `about:blank` shares its creator's process. | Servo multiprocess mode is on. A site (registrable domain) gets one content process, re-execed with `--content-process`, and further tabs for that site reuse it. Pages with no registrable domain (`about:`, `mithu:`, `data:`) stay on one in-process event loop, so a blank tab does not start a process. The shared in-process script thread stays pinned until shutdown, so closing the last blank or internal page does not drop its namespace sender. On Windows, ipc-channel otherwise reports that routed receiver disconnected. The panic text says "script channel", but the `expect` that aborts is the namespace receiver (`constellation.rs` around line 1244 after this patch's line shift). If a script, namespace, service-worker, or hang-monitor receiver still closes, the constellation logs it and retires that receiver. A dead script event loop is marked crashed; the other receivers are not pages. A script thread treats a closed constellation channel as a request to exit. The tab shows "This page crashed" with Reload. Other tabs stay up. A panic on a worker thread is logged and does not open the fatal dialog; that dialog is only for the thread that called `mithu_host::init`. `hard_fail` stays off, so a pipeline panic stays in that tab instead of exiting the process. At four site processes, another site reuses a process that is already running. The processes are unsandboxed. `tools/patch-servo-processes.py` applies that policy to the Servo checkout; the submodule pointer does not change. |
| UI thread vs IO thread | `BrowserMainLoop` runs the UI thread separately from the IO thread. The window never runs Blink. `base::Thread` is a message loop; most work is posted to `base::ThreadPool` sequences. | Servo and the window share the winit thread, because the GL context that presents the page cannot move to another thread. Input is applied there, then the thread returns to winit until the next paint deadline or a Servo wake (`EventLoopWaker` → `EngineWake`). Layout, script, and network stay on Servo's pools and content processes. |
| Thread pool | `base::ThreadPool` runs blocking and sequenced work off the UI thread, with priorities. | `layout_threads`, the async network pool, the canvas pool, and the WebRender pool are set from the machine's parallelism (clamped to 2–8). Style sharing and off-thread JavaScript compilation stay on. |
| Network service | A utility process (or a dedicated thread) owns sockets, the HTTP cache, HTTP/2, and connection reuse. The resource scheduler holds back low-priority requests while HTML, CSS, and render-blocking scripts are in flight. DNS prefetch and preconnect warm connections. | Servo's resource threads are that service, in-process. The HTTP client already negotiates HTTP/2 and keeps six idle connections per host. A 32 MB sqlite disk cache sits under the config directory, with a smaller memory cache (1024 entries) so repeated loads do not stay entirely in RAM. Servo's HTML prefetch tokenizer starts fetches for scripts and sheets it sees while parsing. There is no separate DNS-prefetch or preconnect API, and no embedder hook for Chrome's per-request priority scheduler. |
| Renderer scheduler | `PageScheduler::SetPageVisible` / `SetPageFrozen` throttles and then freezes background pages, including timers. | Hiding a webview makes Servo throttle that document (timers and animation frames). Only the focused tab is shown. Background tabs are not sent to `about:blank`: Servo treats that URL as another site, so the navigation starts a new content process and the previous one stays resident. |
| Memory | `PageDiscardingHelper` drops a background tab's renderer under memory pressure. Site Isolation spends memory to buy a crash boundary. `js_mem_max` is not a Chromium knob, but the renderer heap is capped. | The SpiderMonkey heap cap is 192 MB (Servo's preference cannot be set higher than 255). Session history is 8 entries. The process stays on the system allocator. jemalloc's arenas kept about 100 MB more resident for the same idle blank window, which missed the idle-RAM target. The chrome font book skips faces larger than 1 MB: fontdue keeps every outline, and the CJK fallback alone was about 170 MB. Page text uses Servo's fonts, not that book. |
| Release build | Official builds are optimized and stripped. | The release profile is `opt-level = 3`, thin LTO, one codegen unit, `panic = abort`, and `strip`. The previous profile was `opt-level = "z"` with eight codegen units, which kept the binary smaller and the pages slow. |

YouTube playback still needs a media pipeline Servo does not link in this build (no GStreamer, no Widevine). The page itself is a normal navigation. A codec that needs a patent license is not added here.

GitHub's document reaches `LoadStatus::Complete` in about 8 seconds. The earlier 45 second "never settled" result was the settle check clearing its paint bit at the end of every spin, so a page that painted once and then went quiet never counted. The bit now stays set until the next navigation. After that first complete load, GitHub starts another document and the active tab is `HeadParsed` again; that follow-up is what a later status read shows. No single subresource was identified as stuck.

Closing the window ends the process directly. Servo's constellation teardown waits on each content process, and a busy page can stall that wait, so the window thread does not sit in that teardown.
